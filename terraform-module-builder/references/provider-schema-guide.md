# Provider Schema Introspection Guide

This document explains how the `terraform-module-builder` skill extracts and interprets machine-readable provider schemas via `terraform providers schema -json`. The schema verifies available arguments and types; it does not prove runtime behavior or migration safety.

---

## 1. Why Provider Schema Introspection is Mandatory

Relying solely on web documentation prose introduces significant risks:

- **Provider Version Discrepancies**: Online documentation often displays the `latest` provider version, which may include arguments unsupported by the consumer's installed provider version.
- **Ambiguous Attribute Types**: Documentation often describes complex nested blocks ambiguously; schema JSON provides the exact AST type representation (`attributes` vs `block_types`).
- **Hidden Sensitivity & Computed State**: Schema JSON explicitly marks attributes with `"sensitive": true` and `"computed": true`.
- **Write-Only Arguments**: Write-only arguments (e.g. `secret_string_wo`) are explicitly identifiable in modern framework schemas.

---

## 2. Extracting Schema JSON

To extract the schema for a module:

```bash
# 1. Initialize provider plugins without remote state
terraform -chdir=<module_directory> init -backend=false

# 2. Dump machine-readable schema to JSON
terraform -chdir=<module_directory> providers schema -json > /tmp/provider_schema.json
```

---

## 3. Schema Structure & Field Mapping

The JSON output contains a nested map keyed by provider name:

```json
{
  "provider_schemas": {
    "registry.terraform.io/hashicorp/aws": {
      "resource_schemas": {
        "aws_s3_bucket": {
          "block": {
            "attributes": {
              "bucket": {
                "type": "string",
                "description": "The name of the bucket.",
                "optional": true,
                "computed": true
              },
              "force_destroy": {
                "type": "bool",
                "optional": true,
                "default": false
              }
            },
            "block_types": {
              "cors_rule": {
                "nesting_mode": "list",
                "block": { ... }
              }
            }
          }
        }
      }
    }
  }
}
```

### 3.1. Type Translation Matrix

| Schema JSON Type Representation | Target Terraform HCL Variable Type |
| --- | --- |
| `"string"` | `string` |
| `"number"` | `number` |
| `"bool"` | `bool` |
| `["list", "string"]` | `list(string)` |
| `["map", "string"]` | `map(string)` |
| `["set", "string"]` | `set(string)` |
| `block_types` with `nesting_mode: "list"` | `list(object({...}))` |
| `block_types` with `nesting_mode: "single"` | `object({...})` |

### 3.2. Lifecycle & Exposure Rules

- If an attribute has `"required": true`: It must be mapped to a required variable without a default, or configured with an opinionated module default.
- If an attribute has `"computed": true` and `"optional": false`: It is a read-only output generated by the cloud provider. Do **not** expose it as a variable; expose it in `outputs.tf` if useful to consumers.
- If an attribute has `"sensitive": true`: Any variable or output mapping directly to it should consider `sensitive = true`.
